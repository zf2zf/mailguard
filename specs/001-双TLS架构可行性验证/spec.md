## 一、阶段目标与业务价值

### 1.1 阶段目标

验证 MailShield 采用 HTTP CONNECT、客户端侧 TLS 卸载、独立上游 TLS 会话的 SMTP 代理架构是否可行，并明确 SMTP 明文流量采集和上游 TLS 会话密钥采集的技术边界。

本阶段首先解决关键技术不确定性，不以提前实现完整产品功能为目标。

### 1.2 业务价值

- 确认双 TLS 终止架构的工程可行性，避免在未经验证的方向上投入大量实现工作
- 明确 TLS 1.2 和 TLS 1.3 各字段的实际可获取性，形成可验证的技术基线
- 识别 HTTP CONNECT 与主流邮件客户端的兼容性问题，在正式开发前解决
- 为 Phase 002 的完整架构决策提供技术证据

### 1.3 架构决策前置说明

**以下架构决策尚未正式批准，本 Spec 不代替这些决策。涉及 Constitution 禁止的架构变更时，必须先完成章程修订和 ADR 审批，方可将原型成果正式落地为产品架构**：

| 决策 | 当前状态 | 影响 |
|------|---------|------|
| Constitution Principle I 产品边界 | 现行版本要求 TLS 透明转发，不得擅自改为 TLS 卸载 | Phase 001 验证结果将作为提出新架构决策的依据，但验证本身不等同于批准 |
| ADR-001 go-smtp 补丁策略 | Accepted | 已保护文件不得修改；Phase 001 如需变更 go-smtp 行为，必须提出变更申请 |
| ADR-002 TrafficObserver 策略 | Proposed | 不得将双策略设计当作已批准约束 |
| 客户端证书信任机制 | 尚无 ADR | 需在 Phase 001 验证后提出 ADR |

**本 Spec 的约束**：Phase 001 期间不修改 Constitution、ADR 或现有受保护文件；所有验证代码纳入仓库版本管理，按正式功能开发的目录结构组织，不得静默废弃 `go-smtp`、现有补丁和测试资产。

## 二、用户场景与验收方式

### 场景 0 - 端到端全链路原型（P0）

**描述**：验证完整双 TLS 终止架构的端到端链路：邮件客户端通过 HTTP CONNECT 连接到 MailShield，MailShield 对客户端侧终止 TLS，同时建立到上游 SMTP 服务器的独立 TLS 会话，实现双向 SMTP 明文采集与会话关联。全部组件串接，单一端到端测试覆盖。

**独立验收方式**：构造完整链路，观察双向明文采集结果和双向 TLS 会话建立结果。

**验收标准**：
- 端到端链路建立成功（客户端 → MailShield → 上游 SMTP）
- 客户端侧 TLS 终止生效，客户端可完成 TLS 握手
- 上游 TLS 会话建立成功，可完成 SMTP 交互
- 双向 SMTP 明文均可采集，方向可区分，会话可关联
- **不得仅以 TCP 隧道建立成功作为全链路通过依据**

**TLS 密钥导出的验收**：TLS 密钥导出能力按 FR-001、FR-002 的规则独立验收，不属于场景 0 的验收项；核心密钥无法获取时按 FR-001/FR-002 的已知限制规则处理。

---

### 场景 1 - TLS 1.2 会话密钥采集（P1）

**描述**：邮件客户端通过隐式 TLS（即直接建立 TLS 连接，不经过 STARTTLS 升级）连接 MailShield，MailShield 与上游 SMTP 服务器建立独立 TLS 会话。需要采集上游 TLS 会话密钥（master_secret、随机数、cipher_suite），供外部工具解密 PCAP。

**独立验收方式**：构造 TLS 1.2 连接，通过 KeyLogWriter 或等效机制输出密钥材料，验证每个目标字段非空且格式正确。

**验收标准**：
- `master_secret` 可获取，长度 48 字节
- `client_random` 可获取，长度 32 字节
- `server_random` 可获取，长度 32 字节
- `cipher_suite` 可获取，ID 与实际协商结果一致

---

### 场景 2 - TLS 1.3 会话密钥采集（P1）

**描述**：邮件客户端通过隐式 TLS（即直接建立 TLS 1.3 连接，不经过 STARTTLS 升级）连接 MailShield。需要采集 TLS 1.3 各阶段 traffic_secret 及相关字段。

**独立验收方式**：构造 TLS 1.3 连接，采集 KeyLogWriter 输出，验证各字段可获取性和生命周期。

**验收标准**：
- `client_random`、`server_random`、`cipher_suite` 可获取
- `client_handshake_traffic_secret` 和 `server_handshake_traffic_secret` 可获取
- `client_traffic_secret` 和 `server_traffic_secret` 可获取（密钥更新后新 secret 也可追踪）
- `exporter_secret` 可获取（如 TLS 1.3 应用程序数据使用 exporter）
- `resumption_master_secret` 可获取（会话恢复场景）
- 密钥更新时，新 secret 代系可识别

**待验证事项**：Go 标准库 KeyLogWriter 是否完整覆盖上述所有字段；是否存在 Go 无法导出的字段。

**验证要求**：必须通过实际 TLS 1.3 握手测试验证每个字段的可获取性；验证 Go 标准库 KeyLogWriter 对 TLS 1.3 初始 traffic secret、密钥更新及其他目标字段的实际支持范围，不得预设其能够导出所有后续密钥；密钥更新后新 secret 代系必须可追踪；验证报告必须按字段逐一记录可获取性分类（可直接获取/需其他机制/无法获取）。

---

### 场景 3 - HTTP CONNECT 隧道与 SMTP 协议透传（P1）

**描述**：邮件客户端配置 HTTP CONNECT 代理（CONNECT 方法）连接 SMTP 服务器。MailShield 接收 CONNECT 请求后，建立到目标 SMTP 服务器的 TCP 连接并透传流量（不含 TLS 终止）。此为任意 TCP 隧道能力验证，区分于场景 0 的完整双 TLS 终止架构。

**独立验收方式**：使用 curl、openssl s_client 或模拟客户端，通过 HTTP CONNECT 代理发送 SMTP 命令序列，验证往返通信正确。

**验收标准**：
- HTTP CONNECT 建立成功，TCP 隧道建立
- SMTP 命令可双向透传（明文，无 TLS 终止）
- 连接关闭时隧道正确释放
- 代理能同时处理多个并发 CONNECT 会话

---

### 场景 4 - 客户端信任 MailShield 证书（P1）

**描述**：MailShield 对客户端侧终止 TLS（做 CA），客户端需要信任 MailShield 签发的证书才能建立连接。

**独立验收方式**：使用 openssl 或 TLS 测试工具验证证书链、证书内容、SAN 匹配；记录客户端信任链建立所需的操作步骤和最小条件。

**验收标准**：
- MailShield 可生成带目标 SMTP 服务器 hostname 的证书
- 证书链可被验证（已知 CA 根证书或自签名）
- 明确记录客户端侧证书信任的建立方式（安装根证书、域名匹配规则等）
- 明确隐式 TLS（直接 TLS 连接，不经 STARTTLS）场景下客户端是否接受 IP 地址证书
- **协议模拟工具测试（curl、openssl）**与**真实邮件客户端兼容性**须分别记录，不得混同；未实际测试的客户端必须记录为"未验证"

---

### 场景 5 - 明文流量采集与会话关联（P2）

**描述**：MailShield 终止客户端侧 TLS 后，获得解密后的 SMTP 明文字节流；终止上游 TLS 后，获得上游 SMTP 明文字节流。需要区分双向流并建立关联。

**独立验收方式**：在测试环境中构造双向 SMTP 会话，通过 TrafficObserver 或等效机制输出双向明文字节，验证：
- 客户端侧明文可采集，标记为 client_to_server
- 上游侧明文可采集，标记为 server_to_client
- 同一 SMTP 会话的双向流可通过连接标识关联

**验收标准**：
- 双向解密后字节流均可采集
- 方向可区分（client_to_server / server_to_client）
- 同一会话双向流可关联（通过连接 ID、时间戳等）
- AUTH 凭证明文行可识别（用于后续过滤设计）

**注意**：本阶段仅验证可采集性，不实现过滤逻辑；过滤需求在 Phase 002 Spec 中定义。

---

### 场景 6 - STARTTLS 与隐式 TLS 评估（P2）

**描述**：评估 STARTTLS（显式 TLS）和隐式 TLS（隐式 TLS，即端口 465/587 直接 TLS）在双 TLS 终止架构下的处理差异。按协议行为（而非端口号）定义测试场景。

STARTTLS 验证所需的最小 SMTP 协议状态处理范围：**检测 STARTTLS 命令（`STARTTLS` 关键字）、触发 TLS 握手升级、验证握手完成后明文命令可继续处理**。此范围不构成"完整 SMTP 协议解析"——不解析 EHLO/MAIL/RCPT/DATA 等命令内容，仅处理 TLS 升级本身的状态转换。

**独立验收方式**：分别构造 STARTTLS 和隐式 TLS 连接，按协议状态转换验证两种模式的核心行为差异。

**待验证事项**：
- STARTTLS 场景：MailShield 是否需要在 STARTTLS 之后重新建立 TLS 隧道
- 隐式 TLS 场景：MailShield 在 CONNECT 阶段是否即终止 TLS
- 两种模式对 TrafficObserver 连续性的影响（参考 ADR-002 中 handleStartTLS 调用 init() 的描述）

**验收标准**：
- 明确隐式 TLS 和 STARTTLS 的技术差异（按协议状态，不按端口号）
- 明确两种模式对双 TLS 架构的影响差异
- 至少验证隐式 TLS 和 STARTTLS 的核心状态转换
- 识别需要新增的架构决策（如有）

## 三、功能需求

### FR-001：TLS 1.2 密钥材料采集

系统必须能够采集 TLS 1.2 连接中以下字段。验证报告必须按字段逐一标记可获取性：

| 字段 | 可获取性 | 备注 |
|------|---------|------|
| `client_random` | 待验证 | |
| `server_random` | 待验证 | |
| `cipher_suite` | 待验证 | |
| `master_secret` | 待验证（核心密钥） | PCAP 解密必需 |

必须通过实际测试验证每个字段的可获取性。不得伪造或不可靠推导任何字段值。

**核心密钥材料无法获取时的验收处理**：若 `master_secret` 经验证无法通过 KeyLogWriter 获取，Phase 001 必须记录为已知限制，并评估替代方案的可行性；不得将此项标记为"通过"，但也不得因此阻止阶段完成。整体阶段通过条件按 9.7 门槛执行。

### FR-002：TLS 1.3 密钥材料采集

系统必须能够采集 TLS 1.3 连接中以下字段。验证报告必须按字段逐一标记可获取性：

| 字段 | 可获取性 | 备注 |
|------|---------|------|
| `client_random` | 待验证 | |
| `server_random` | 待验证 | |
| `cipher_suite` | 待验证 | |
| `client_handshake_traffic_secret` | 待验证 | |
| `server_handshake_traffic_secret` | 待验证 | |
| `client_traffic_secret` | 待验证（核心密钥） | 密钥更新后新代系 secret 必须可追踪 |
| `server_traffic_secret` | 待验证（核心密钥） | 密钥更新后新代系 secret 必须可追踪 |
| `exporter_secret` | 待验证 | 如 TLS 1.3 应用程序数据使用 exporter |
| `resumption_master_secret` | 待验证 | 仅会话恢复场景适用 |

必须通过实际测试验证每个字段的可获取性。密钥更新后新代系 secret 必须可追踪。验证报告必须明确区分三类字段：可直接获取、需其他机制获取、当前机制无法获取。不得伪造或不可靠推导任何字段值。

**核心密钥材料无法获取时的验收处理**：若 `client_traffic_secret`/`server_traffic_secret` 经验证无法获取，Phase 001 必须记录为已知限制，并评估替代方案的可行性；不得将此项标记为"通过"，但也不得因此阻止阶段完成。整体阶段通过条件按 9.7 门槛执行。

### FR-003：HTTP CONNECT 代理能力

系统必须支持 HTTP CONNECT 方法建立 TCP 隧道，转发任意 TCP 流量（不只是 HTTP），并正确处理隧道生命周期（建立、维持、关闭）。

### FR-004：客户端 TLS 终止

系统必须能够对客户端侧 TLS 连接进行终止（作为服务器端），并生成目标服务器 hostname 的证书，支持 RSA 和 ECDSA 证书类型。

### FR-005：上游 TLS 会话建立

系统必须能够与目标 SMTP 服务器建立独立 TLS 会话（作为客户端），支持 TLS 1.2 和 TLS 1.3。

### FR-006：双向明文流量采集

系统必须能够采集双向解密后的 SMTP 明文字节流，并区分 client_to_server 和 server_to_client 方向。

### FR-007：会话双向流关联

同一 SMTP 会话的双向流必须可通过唯一连接标识关联；关联机制必须在验证报告中明确说明。

### FR-008：KeyLogWriter 接口验证

Go 标准库的 KeyLogWriter 接口是 TLS 密钥导出的主要机制，但不一定能覆盖所有目标字段。验证结果必须明确记录：
- 可直接获取的字段及其格式
- 需其他机制获取的字段及其替代方案
- 当前机制无法获取的字段（标记为已知限制）

不得假定 KeyLogWriter 可以直接提供所有目标字段；验证以真实测试结果为依据。

## 四、非目标（Out of Scope）

以下内容不属于 Phase 001：

- **不实现** SMTP 协议解析、业务逻辑或邮件投递
- **不实现** 过滤逻辑（包括 AUTH 凭证过滤）
- **不实现** PCAP 解密引擎
- **不实现** 持久化存储
- **不实现** 配置管理系统
- **不实现** 生产级部署配置
- **不假设** TLS 1.3 KeyLogWriter 完整覆盖所有字段（必须实际验证）

## 五、范围边界

### 5.1 技术边界

- 原型代码纳入仓库版本管理，按正式功能开发的目录结构组织（如 `cmd/`、`internal/` 等），作为后续阶段演进基础

### 5.2 架构约束边界

- 不得修改 Constitution
- 不得修改任何 Accepted ADR
- 不得修改 `third_party/go-smtp/` 下的受保护文件
- 不得修改 `tests/` 下的测试资产

### 5.3 验证环境边界

- 验证在本地环境（localhost）进行，无需外部 SMTP 服务器
- 使用自签名证书进行 TLS 测试
- 客户端测试可使用 curl 或 openssl s_client 模拟，不强制要求真实邮件客户端
- **敏感数据保护**：明文采集验证仅使用虚构 SMTP 测试数据和虚构认证凭证；测试日志、报告及临时文件不得泄露认证数据；验证完成后必须清理所有临时文件和测试数据

## 七、敏感数据保护

Phase 001 验证过程中必须遵守以下数据保护要求：

- **测试数据**：仅使用虚构 SMTP 测试数据和虚构认证凭证
- **日志与报告**：测试日志、报告及临时文件不得包含真实认证数据
- **密钥日志**：TLS 密钥日志（KeyLogWriter 输出）不得提交到版本库；验证过程中生成的密钥日志文件必须包含虚构测试密钥，验证完成后即删除；不得以"测试数据"为由提交真实密钥
- **清理要求**：验证完成后必须清理所有临时文件和测试数据（包括密钥日志）
- **边界**：明文采集验证仅验证可采集性，不实现过滤逻辑；过滤需求在 Phase 002 Spec 中定义

## 八、风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| Go KeyLogWriter 无法导出 TLS 1.3 全部字段 | 高 | Phase 001 优先验证，识别缺失字段后提出 ADR |
| HTTP CONNECT 不被某些邮件客户端支持 | 中 | 通过多种客户端验证，记录兼容性问题 |
| 客户端证书信任建立复杂度过高 | 中 | 明确最小信任建立条件，评估可行性 |
| Constitution 限制导致双 TLS 架构无法推进 | 高 | Phase 001 结果作为提出 ADR 的技术依据 |
| STARTTLS 场景下 TrafficObserver 连续性不确定 | 中 | 记录为待验证事项，在 Phase 001 中观察 |

## 九、验收标准（Phase 001 完成条件）

以下标准必须全部满足，方可认为 Phase 001 完成：

### 9.1 TLS 密钥采集验证

- [ ] TLS 1.2：`master_secret`、`client_random`、`server_random`、`cipher_suite` 按字段逐一验证，记录可获取性分类；可获取字段验证非空且格式正确
- [ ] TLS 1.3：FR-002 中的每个字段按字段逐一验证，记录可获取性分类；密钥更新后新 secret 代系可追踪
- [ ] 验证报告明确区分三类字段：可直接获取、需其他机制获取、当前机制无法获取
- [ ] 不得伪造或不可靠推导任何字段值；验收以真实测试结果为依据
- [ ] TLS 1.2 和 TLS 1.3 的密钥生命周期（首次握手生成时间点）已记录

### 9.2 HTTP CONNECT 与全链路验证

- [ ] HTTP CONNECT 隧道可成功建立并维持
- [ ] SMTP 命令序列可双向透传
- [ ] 至少一种邮件客户端或模拟工具验证通过
- [ ] 并发 CONNECT 会话可同时维持（至少 5 并发）
- [ ] 端到端全链路原型验证通过（场景 0，全链路串接）

### 9.3 客户端证书信任验证

- [ ] MailShield 可生成目标 hostname 证书（测试用）
- [ ] 客户端信任链建立方式已记录（操作步骤）
- [ ] 证书验证失败时客户端行为已记录

### 9.4 明文流量采集验证

- [ ] 双向 SMTP 明文均可采集，方向可区分
- [ ] 双向流可通过连接标识关联
- [ ] AUTH PLAIN/LOGIN 命令行可识别（标记，不做过滤）

### 9.5 STARTTLS 评估

- [ ] STARTTLS 和隐式 TLS 的行为差异已记录
- [ ] 对 TrafficObserver 连续性的影响已观察并记录
- [ ] 需要新增的架构决策已列出（如有）

### 9.6 技术基线兼容性

- [ ] 现有 13 项集成测试全部通过（验证未破坏现有功能）；测试结果已记录
- [ ] 无修改 Constitution、ADR 或受保护文件
- [ ] 原型代码纳入仓库正式工程结构，保留为后续阶段演进基础

### 9.7 进入 Phase 002 的门槛

Phase 002 开始前，必须满足：
1. 所有 Phase 001 验收标准已通过并经用户确认
2. **涉及与现行 Constitution 冲突的正式架构实现时，必须先完成必要的章程修订批准和相关 ADR 的 Accepted 决策；仅 Proposed 状态不足以推进正式落地**
3. Constitution 相关修订已提出（如 TLS 透明转发约束需变更）
